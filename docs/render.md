# 渲染层（`crates/render`）

> 状态：✅ **已实现**（2026-09-19）· 测试：12 单测 + 15 集成 · 冒烟：`scripts/smoke.sh` §8（9 项）
>
> 一句话：**把场景变成能被判读、能被核对、能被当证据的静态观测图。**

---

## 1. 它交付三件事

| # | 交付 | 为什么 |
| --- | --- | --- |
| 1 | **看得见**：多视角静态快照 → PNG（CLI 落盘 / MCP 直接返回图片） | Agent 与人共用的"眼睛"。MCP 里返回 `image/png`，多模态模型可以直接看 |
| 2 | **判得准**：`id pass` —— 每个像素属于哪个对象 | 精确拾取、按对象统计像素、以及**量出「窗前挡光带被遮挡了多少 %」** |
| 3 | **对得上账**：同场景同参数 ⇒ 同像素哈希 | 图像因此能当**证据**（"回滚后画面逐像素一致"是 H0 的验收项，靠它来断） |

第 2 条是最容易被低估的：**一旦每个像素都知道自己属于谁，"图"就变成了"可计算的观测"**。
`band_occlusion` 就是这么来的——它把「沙发挡窗」从一句形容变成一个数字（实测 H0 场景：**50%**）。

## 2. 边界：渲染只是视图

- 依赖是**单向**的：`render → core`。`core` 不许 import `render`。
  所有评测维度都必须在没有渲染的情况下也能算——否则"引擎可离线"就是假的。
- 渲染**不是**判据的来源。判断几何关系请以 `scene_observe` 的数字为准；
  图是给人/模型快速建立空间感的，不是测量工具（测量由 `id pass` + 规则层负责）。

## 3. 为什么先做 CPU 软件光栅

| 理由 | 说明 |
| --- | --- |
| **确定性** | GPU 的浮点行为、光栅化细则、驱动版本都会影响像素；而这里的图要当证据 |
| **无宿主依赖** | `cargo test` 就能跑，不需要 GPU / 浏览器 / 窗口系统 |
| **够用** | H0 的几何是包围盒（真实几何要等 `io`），画的本来就是示意图而非照片 |

GPU 后端（wgpu：WebGPU → WebGL2 → 仅网格）会在接真实网格/高斯时作为**性能档**加进来，
但**观测契约不变**：多视角 + id pass + 指标。换了后端必须显式声明
[`Rendered::degraded`](../crates/render/src/lib.rs)，不许悄悄换画质——
"无 WebGPU 就显式降级并声明观测不可信"是写进设计里的要求。

## 4. 四个视角，以及为什么必须四个

| 视角 | 内容 | 类型 |
| --- | --- | --- |
| `top` | 平面布置图（+X 向右、+Z 向下 ⇒ **北在上**） | 正交 |
| `front` | 正立面（从 +Z 往 -Z 看，即朝着窗户那面） | 正交 |
| `iso-sw` / `iso-se` | 西南 / 东南 45°、仰角 30° | 透视 |

视角**从房间包围盒推导**（不存相机参数），所以同一个场景永远得到同四张图。

关键在于**面是朝向敏感的**，这条测试写明了原因：

- 水平面（地面、挡光带）在 `front` 里**必然退化成一条线**；
- 垂直面（窗）在 `top` 里**必然退化成一条线**。

所以单靠一个视角一定会漏东西；而"北在上"的平面图里，「窗在哪」是靠**挡光带地面标记**表达的。
四视角 + id pass 的组合，正是「Agent 的观测给可判读的静态观测」这条红线的落地方式。

## 5. id pass 与遮挡测量

特殊 id 与对象 id 分开，这样统计不会被装饰物污染：

| id | 含义 |
| --- | --- |
| `0` | 背景 |
| `1..=N` | `scene.objects[i-1]`（场景顺序即 i） |
| `0xFFFFFFF0` / `F1` / `F2` / `F3` | 窗 / 挡光带 / 房间线框 / 地面 |

`is_object(id)` 只认 `1..=N`，所以「物体可见像素」与「挡光带遮挡」这两类统计天然干净。

**挡光带遮挡比例**怎么算：俯视图里把挡光带三角形栅格化成一张**不看遮挡**的区域掩码，
再数其中被「真实对象」盖住的像素占比。这样即使挡光带被家具完全盖住，分母依然正确。

## 6. 确定性的边界（写清楚，别过度承诺）

- **同平台同构建**：逐字节可复现（像素哈希稳定）。debug 与 release 之间也一致
  （Rust 不做 fast-math，同样的运算顺序给同样的结果）。
- **跨平台**：`sin/cos` 由平台 libm 提供，末位可能有差异 ⇒ 像素级逐字节一致**不承诺**。
  跨平台的评测口径应当用 `id pass` 统计与规则指标（那些是整数/有理数运算），
  而不是像素哈希。
- PNG 是**无损**的（编码-解码往返逐字节一致，测试里断言过）。
  但**比较请用 `image_hash`（原始像素的 sha256）而不是 PNG 字节**——
  换编码器/压缩级别时前者不变，后者会变。

## 7. 怎么用

```bash
# CLI：落盘四个视角
rsi3d-harness scene render scene.json --out shots --width 640 --height 480
# → shots-top.png · shots-front.png · shots-iso-sw.png · shots-iso-se.png
# 同时打印：每个对象的可见像素数（0 = 被完全遮住）与窗前挡光带被遮挡 %

# 只要一张
rsi3d-harness scene render scene.json --views top --out shot
```

MCP 里是 `scene_render`，**直接返回图片内容**：

```json
{"name": "scene_render", "arguments": {"views": ["top", "iso-sw"], "width": 320, "height": 240}}
```

默认只出 `top`（对「挡没挡住窗」最有信息量，且单张图上下文开销最小）。
320×240 的两视角约 12–13 KB base64——**图片是有成本的**，所以默认克制、按需增加。

## 8. 还没做

| 项 | 说明 |
| --- | --- |
| 真实几何 | 现在画的是 AABB 盒子。`io` 落地后换成网格，**光栅器与观测契约都不用改** |
| 高斯 / 点云 | `LayerKind::Gaussian/Points` 目前按包围盒画（并在 `degraded` 里说明），不是真 3DGS |
| GPU 后端 | wgpu 作为性能档；接入真实资产的量级后才需要 |
| 图上文字标注 | 对象名/尺寸标在图上需要字体渲染，暂不做——身份靠同时返回的文本与结构化摘要 |
| 材质外观 | 现在是按角色+材质的纯色（要"一眼分得清"），不做 PBR |

## 9. 踩坑（都是真的）

1. **斜视相机距离不能拍脑袋**。第一版用 `radius * 3.4`，结果画面 95% 是空白。
   正确做法是按「包围球正好落进竖直视场」算：`dist = radius / sin(fov/2)`。
2. **别用 `thread_local` 传视口**。第一版为了让投影函数保持无参而用了线程局部状态，
   那是隐藏状态、不可重入——改成把画布尺寸显式传下去。
3. **朝向敏感这件事必须写进测试**，否则很容易把"垂直面在俯视图里没有面积"误判成渲染 bug。
   测试里两处 `assert_eq!(..., 0)` 就是专门记录这个几何事实的。
4. **对比度决定可读性**：地面最初用 `[222,226,230]`、背景 `[244,246,248]`，
   结果房间轮廓糊在背景里、家具像浮在空中。拉开明度差之后才好读。
